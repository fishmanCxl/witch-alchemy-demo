# WeChat Mini Game Production Guide

## Architecture boundaries

- `assets/scripts/core/` is framework-free TypeScript. It must never import `cc`, reference `wx`, access storage, play audio, or schedule presentation timers.
- `assets/scripts/presentation/` owns Cocos nodes, input, animation, particles, audio timing, and scene transitions. It consumes immutable results from `core`.
- `assets/scripts/platform/` is the only client directory allowed to reference WeChat APIs, rewarded video, network state, Storage, or CloudBase.
- `assets/resources/game/` is generated from approved prototype runtime assets by `tools/sync-approved-assets.mjs`. Never copy from `prototype/artifacts/chibi-raw`.
- `cloudbase/` owns trusted identity, progress revision, reward idempotency, configuration, and result telemetry. Never accept OPENID from client input.

## Product invariants

- Sharing uses the native WeChat share card without a custom image or reward. Home keeps a third square share entry below settings and collection; level completion uses compact replay and share actions on the top row plus one wide primary action below; regular completion advances to the next level/chapter or returns to level select, while daily completion returns home. Collection detail keeps return and share actions side by side.
- Level completion keeps its title at the top of the panel, distributes the three information rows and star row evenly below it, shows only `✦ 完美炼成` for a theoretical-optimum clear, and renders the shared 80×80 earned/empty star SpriteFrames at 44px with 68px center spacing. Selector stars use the same SpriteFrames at 15px with 18px center spacing, and the chapter total uses the earned SpriteFrame at 44px instead of a text glyph.
- All interface text rendered through the shared label path uses a crisp 1px lower-right deep-purple shadow at roughly 55% opacity.

- Fixed 5×3 slots; regular content uses at most 14 and slot index 14 is the one-time rewarded empty bottle.
- Completed bottles fly away and become `vanished`; slots never reflow or become reusable.
- When a selected bottle cannot pour into another active filled bottle, keep the invalid feedback on both bottles but transfer selection and the cyan highlight to the newly tapped bottle immediately.
- Bottle interactions must refresh the mounted level nodes; never destroy and rebuild the full production surface for selection, invalid feedback, pouring, or witch-state settling.
- Bottle capacity is four and only a contiguous matching top run can pour.
- A selected bottle keeps its existing lift and cyan highlight, then sways by 5 degrees left and right on its visual node only. On a valid pour, pause that sway, keep the source lifted, and hold a 28-degree tilt toward the target column until the 520ms pour state ends; targets in the same column default to a left tilt. Never move the hit target or board slot for these animations.
- Witch runtime states and frame counts are idle 18, prepare 12, raise 12, cast 20, celebrate 14, return 18, and oops 12.
- Wide raster buttons must match the approved prototype with nine-slice rendering: preserve the 72px source corners at one-third display scale and stretch only the center. Bottom control bases remain square and centered inside their wider 110×72 hit targets; never SIMPLE-stretch square button artwork into a rectangle.
- Ordinary play and local save work offline. Reward claims require a successful online cloud response.
- Stamina is an independent local record capped at 10, recovers 1 point every 30 minutes, and gains 5 points (still capped at 10) only after a completed rewarded ad; that ad reward is local-only and does not make a cloud claim. Entering a level costs nothing, while successful completion and confirmed exit each spend exactly 1 point. Cancelled exit, restart, undo, background/foreground transitions, and force-close never spend stamina.
- The home stamina pill uses 4px horizontal and 2px vertical content padding with a 2px row gap. When stamina is below 10, append the existing 18px plus badge and keep the whole pill as the single trigger for the stamina dialog; hide the badge and shrink the pill immediately at full stamina.
- The home stamina pill uses the approved circle-free purple-and-gold 166×34 single-resolution SpriteFrame at its maximum width, including 10px trailing clearance after the plus badge, shrinks dynamically to 136×34 when full, and keeps the heart centered in the left inset.
- The home stamina pill aligns its vertical center with the native WeChat menu capsule by normalizing `wx.getMenuButtonBoundingClientRect()` against the WeChat window height and converting that ratio through the current Cocos visible height; use design-space `y: 365` only when the platform metrics are unavailable or invalid.
- The separate green plus badge beside the bottom add-bottle control is not rendered. All rewarded actions share `REWARDED_AD_CONFIG`: until WeChat ads are available its global `mock` mode completes rewards without opening an ad, while `wechat` mode uses the configured real ad and keeps the empty-bottle cloud claim. Develop and trial builds expose one in-memory “广告状态 · 通过/失败” settings switch that overrides the shared ad result for every rewarded action; release builds never expose that switch.
- Each regular, daily, or endless challenge starts with three undos and one restart. Successful uses consume only their own allowance; restarting never refills undo or counts as an endless failure. Regular and endless allowances persist with their active snapshots, while daily allowances live only for that daily attempt. At zero, the corresponding control hides its allowance bubble and shows only the rewarded-ad badge; a completed ad refills that allowance to its maximum and immediately performs the requested action. Positive undo and restart allowances use the home daily-commission bubble's right-side position and gentle vertical float, showing only the remaining digit. The add-empty-bottle control always shows the rewarded-ad badge and is available in endless mode.
- Chapters one through ten publish exactly levels 1–300 from checked static data, with 30 levels per chapter. Runtime code must never generate or solve levels; use the ten chapter generation tools and commit their deterministic outputs/reports. Level 301 remains unpublished.
- Level 1 is the only authored tutorial; levels 2–30 use the full all-colors rules, level 12 keeps the legacy board byte-for-byte, and generated difficulty rises sharply from level 2 before the approved late-chapter peak and easing.
- Chapter two starts hard at target 0.88 on level 31, rises through 0.96/0.97 on levels 32/33, peaks at 1.05 on levels 55–57, and eases to 0.98 on level 60; accepted boards still pass the configured optimal-move, segment, explored-state, opening-move, and misleading-branch gates.

- Chapter generators with expensive exact solving must separate discovery from routine verification. `--search` is the intentional full candidate scan, `--check` reconstructs committed boards from locked attempt/seed values and validates static data plus reports without calling the exact solver, and `--verify-solver` explicitly reruns the locked boards through the solver. For later chapters, apply cheap segment/opening filters before solving, set an evidence-backed explored-state cap, sample acceptance rates before a full sweep, and freeze every accepted attempt before routine checks. A chapter search must stop for calibration rather than exceed 1,000 attempts or 10 minutes per level.
- The board has 14 ordinary slots plus reserved reward slot index 14. With two initial empty bottles, no chapter may exceed 12 colors; chapters seven through ten remain fixed at 11 colors, and later chapters must not increase color count automatically from a target coefficient.
- Each chapter selector shows all 30 levels in one fixed 5×6 page with no scrolling or pagination. Chapter arrows switch between published chapters; chapters two through ten remain disabled until levels 31, 61, 91, 121, 151, 181, 211, 241, and 271 are unlocked.

The chapter heading, arrows, star total, and 5×6 grid move down together when needed so the runtime menu-aligned settings trigger keeps a 12px vertical gap above the left chapter arrow; chapter refresh must reapply the same offset.
- While the level selector stays open, chapter arrows keep the background and common controls mounted, rebuild only the chapter-specific title/arrows/grid, and synchronously reuse already loaded SpriteFrames instead of issuing repeated asynchronous loads.
- Completing levels 30, 60, 90, 120, 150, 180, 210, 240, and 270 unlocks and advances to levels 31, 61, 91, 121, 151, 181, 211, 241, and 271. Completing level 300 caps progress at level 300 and returns to the tenth-chapter selector; level 301 remains unpublished.

## Verification

- Never destructure a `Set` directly in production Cocos TypeScript: Creator's loose transpilation can emit indexed access such as `set[0]`, which is always undefined. Convert ordered transient sets with `Array.from(set)` first, and validate animation-state changes against a built Cocos runtime by sampling the affected node over time rather than checking source text alone.
- Every newly added PNG loaded through a `resources` path ending in `/spriteFrame` must have `userData.type: "sprite-frame"` and an `@f9941` sprite-frame subresource in its `.meta`. After the WeChat build is prepared, verify the resources config contains that `/spriteFrame` path; a texture-only import is not a usable runtime SpriteFrame even when the PNG itself exists in the project.
- For a narrowly scoped fix to one authored level's config or completion behavior, run only that level's focused tests plus the normal WeChat build/package checks; do not rerun the full chapter generator/solver or the entire test suite.
- Run `node --experimental-strip-types tools/generate-levels.ts --check`, the fast `node --experimental-strip-types tools/generate-chapter-six.ts --check`, and `node --experimental-strip-types --test tests/*.test.ts` only after shared core rules, generation algorithms, or chapter-wide data change. Reserve `tools/generate-chapter-six.ts --verify-solver` for solver/gate changes or final release evidence; never use the multi-hour `--search` path as a routine consistency check.
- Run CloudBase tests and `tools/prepare-functions.mjs` after changing shared progress, rewards, telemetry, or cloud functions; all copied runtime hashes must match.
- Open the project in Cocos Creator 3.8.8 before claiming scene or WeChat build compatibility. Cocos generates `.meta` files on first import; retain those generated metadata files afterward.
- After every WeChat build, run `tools/prepare-wechat-build.mjs` and preview from a fresh Developer Tools process. The uploaded `resources` subpackage must contain the complete Cocos bundle rather than only its JavaScript entry; its non-empty `config.json` must be protected by both the `subpackages/resources/` folder include and the exact `subpackages/resources/config.json` file include in `project.config.json`; preparation must fail instead of producing a QR code when that manifest is absent. Its `game.js` must directly contain the Cocos `System.register` bundle entry, never `require('./index.js')`, because a fresh WeChat subpackage context does not register that sibling module before executing its entry. Restart the IDE service after changing `project.config.json` packaging rules.
- Local file checks and automated tests are not phone-preview verification. Before claiming phone compatibility, use the official Developer Tools CLI to upload a fresh preview with the production AppID, verify the reported main/subpackage sizes, and have the new QR code opened successfully on a phone; never reuse an older QR code. Every package test must restore `build/wechatgame/project.config.json` in `finally`, and the final prepared package must retain the configured production AppID, the full `subpackages/resources/` include rule, and a non-empty `subpackages/resources/config.json`.
